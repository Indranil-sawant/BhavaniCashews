STEP 1: SEARCHING WITHOUT AN INDEX (LINEAR TIME - O(N))
--------------------------------------------------------------------------------
Imagine you have a table containing 1,000,000 (one million) product rows.
The products are stored in the database in the order they were inserted, which 
means their names are unsorted.

You run this query:
  "Find the product named 'Premium W320 Whole Cashews'"

Without an index, the database engine must start at the very first row and read 
every single row one-by-one until it finds a match (or finishes the table).
This operation is called a TABLE SCAN (or Sequential Scan).

- If the product is at the first row: 1 check.
- If it's at the last row: 1,000,000 checks.
- On average: 500,000 checks.

In computer science, we measure this using Big-O notation. 
Big-O measures the "worst-case scenario" growth rate of an algorithm.
For a table scan, the time taken grows linearly with the number of rows (N).
We call this Linear Time Complexity, written as:

  ===> O(N) (pronounced "Big O of N")

If N is 1,000,000, we do 1,000,000 checks. If N grows to 10,000,000, we do 
10,000,000 checks. It scales poorly and slows down as the database grows.

--------------------------------------------------------------------------------
STEP 2: THE SOLUTION: LOGARITHMIC TIME - O(log N)
--------------------------------------------------------------------------------
Now, imagine the products are sorted alphabetically. 

Instead of starting from the beginning, you can use the "Phonebook Search" method, 
technically known as Binary Search:
1. Open the phonebook exactly in the middle.
2. If the name you want is alphabetically earlier than the middle name, you 
   throw away the right half.
3. If it's later, you throw away the left half.
4. Repeat this process with the remaining half.

Every single check cuts the search space in half!
Let's see how many checks it takes to search through 1,000,000 products:
- Start: 1,000,000 items
- Check 1: 500,000 items left
- Check 2: 250,000 items left
- Check 3: 125,000 items left
- Check 4: 62,500 items left
- Check 5: 31,250 items left
- Check 6: 15,625 items left
- Check 7: 7,812 items left
- Check 8: 3,906 items left
- Check 9: 1,953 items left
- Check 10: 976 items left
- Check 11: 488 items left
- Check 12: 244 items left
- Check 13: 122 items left
- Check 14: 61 items left
- Check 15: 30 items left
- Check 16: 15 items left
- Check 17: 7 items left
- Check 18: 3 items left
- Check 19: 1 item left
- Check 20: Found it!

To search 1,000,000 sorted items, it takes a maximum of 20 checks!
This relationship is defined by logarithms (specifically log base 2).
Mathematically: 2^20 = 1,048,576.
We call this Logarithmic Time Complexity, written as:

  ===> O(log N) (pronounced "Big O of log N")

Look at the difference:
- O(N) search on 1M rows: 1,000,000 operations.
- O(log N) search on 1M rows: 20 operations.
This is a 50,000x speedup!

--------------------------------------------------------------------------------
STEP 3: HOW DATABASES DO IT: THE B-TREE INDEX STRUCTURE
--------------------------------------------------------------------------------
A database index is a copy of a column (or columns) that is kept in a sorted data 
structure. In PostgreSQL, MySQL, and SQLite, this is usually a B-Tree (Balanced Tree).

Think of a B-Tree as a hierarchy of nodes:
- Root Node: The entry point (e.g., has ranges like "A-G", "H-P", "Q-Z").
- Branch Nodes: Middle routing tiers that point to narrower ranges.
- Leaf Nodes: The bottom level containing the sorted values and pointers to the 
  actual row locations on the hard drive.

Example search for "Cashews" in a B-Tree index:
                       [ Root Node ]
                        /    |    \
                   "A-G"   "H-P"   "Q-Z"
                    /
            [ Branch Node ]
             /     |     \
         "Aa-Cc" "Cd-Ef" "Eg-Gz"
           /
      [ Leaf Node ]
      "Artisanal Cashews" ---> points to physical Hard Drive Block #4582

Because the tree is "balanced" (all leaf nodes are at the same depth), search 
efficiency is guaranteed to be O(log N).

--------------------------------------------------------------------------------
STEP 4: COMPOSITE INDEXES: THE ORDER OF COLUMNS MATTERS
--------------------------------------------------------------------------------
Often, you query data filtering on multiple conditions. For example:
  "Find products where category = 'Raw Organic' AND is_available = True"

If you only index `category`, the database will use O(log N) to find the category, 
but then must do a table scan on those results to check `is_available`.

To solve this, we create a COMPOSITE INDEX (an index on multiple columns).
A composite index behaves like a telephone directory ordered by:
  [Last Name, First Name]

You can easily look up "Smith, John" because the directory is sorted first by 
Last Name, and then by First Name.
But can you look up people named "John" if you don't know their last name? 
No! You would have to scan the entire book.

Rule of thumb:
- An index on (A, B, C) can speed up queries filtering on:
  - (A)
  - (A, B)
  - (A, B, C)
- It CANNOT speed up queries filtering only on (B) or (C) without A.
This is called the Left-Prefix Rule.

STEP 5: HOW OUR CODE CHANGES SAVED YOUR APPLICATION
--------------------------------------------------------------------------------
Let's look at the indexes we added to your Product model and why they matter:

1. models.Index(fields=['is_available', '-created_at'])
   - Query Optimized: The "newest products" query on your homepage.
   - SQL Query: `SELECT * FROM products WHERE is_available = True ORDER BY created_at DESC`
   - How it works: Because the index is sorted by availability, and then by 
     date (in descending order), the database can instantly pull the newest 
     available items. Complexity is O(log N) instead of an O(N) table scan 
     followed by a slow in-memory filesort.

2. models.Index(fields=['category', 'is_available', '-created_at'])
   - Query Optimized: Category-specific product pages (e.g., clicking 'Slow-Roasted').
   - SQL Query: `SELECT * FROM products WHERE category_id = 5 AND is_available = True ORDER BY created_at DESC`
   - How it works: The index is sorted first by category, then availability, 
     then date. The database jumps directly to the category block, checks availability, 
     and reads products in reverse chronological order instantly. O(log N) speed.

Without these indexes, as you upload more products and receive more reviews, 
your pages would take seconds to load. Now, page load times remain constant 
(fractions of a millisecond) even if your inventory grows to millions of products!
